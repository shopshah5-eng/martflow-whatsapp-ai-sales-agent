# Custom websites and review requests — staging handoff

## Current scope and important limits

These are **foundations, not a finished deployment**. No custom website exists in this repository. No customer WhatsApp review message is sent by this implementation: `deliveryAvailable` is always false and records are deliberately locked to `awaiting_delivery_setup`. Do not describe a prepared request as sent, and do not enable a sender simply by changing a flag. The website API supports catalogue reading and edits to existing product text; it does not yet create products, receive pictures, handle WhatsApp submissions, or update an actual website. AI conversational learning remains a separate, opt-in/reviewed feature and is not made self-improving by this change.

## Review requests

- Owners/admins with conversation access can save an HTTPS Google-hosted link and enable request preparation on the Leads screen. URL validation restricts hosts but **does not verify that the link belongs to the business or opens the correct review page**; verify it separately.
- The owner explicitly confirms the deal and customer permission. The UI marks a selected lead `converted` if needed and then requests preparation. If preparation fails after status changed, the UI says so. Past leads are handled individually, not in bulk. An API caller must also provide explicit confirmations and the lead must already have `converted`, `won` or `completed` status.
- Request records are tenant-scoped and unique per normalized phone and workspace, even across leads. This conservative rule has no resend, delete or cancellation UI yet. A lead deletion cascades the prepared record, so a future sender needs a separate persistent deduplication ledger. Conversation existence and contact eligibility are not established by the queue. Consent here is an operator attestation, not independently collected evidence. Opt-out lookup is checked on preparation and fails closed on DB errors, but the existing opt-out persistence/ingestion has known defects. **Never infer a future send is safe from queue presence alone.**
- The staging SQL restricts the new tables to the service role and does not create a delivery worker. Existing broad live policies on other objects remain a separate blocker. Roll out only after schema inventory, backup, staging validation and explicit approval.
- To finish automatic delivery: first fix durable opt-out ingestion/cancellation across the actual WhatsApp ingress path; collect auditable, appropriately scoped consent and a way to withdraw it; implement an atomic durable claim and idempotency record, a configurable delay, cancellation, and a no-blind-retry state for ambiguous provider results; recheck consent, current opt-out, deal status and configuration immediately before sending. Use the actual WhatsApp provider's applicable 24-hour window/approved-template rules. Send neutral review invitations, with no incentives or sentiment filtering. Validate rate limits and provider response semantics using mocks, then explicitly consented staging numbers. Review each historical candidate separately; do not bulk-message old customers.

## Custom website API

A signed-in superadmin or explicitly granted catalogue manager may rotate/revoke a single key for an approved workspace in the catalogue admin portal. The secret appears once and is stored only as a SHA-256 hash. Integrations fail closed when the issuing user's live membership or grant is revoked. A superadmin must be an actual signed-in profile; the shared platform header cannot issue a key. The integration must be deactivated or rotated upon a compromise. This key grants catalogue access for its workspace, not inbox, workspace settings, pairing or review requests.

The website developer must store the secret in **server-side secret storage**, never in browser HTML, JavaScript, URLs or logs, and enforce logged-in editor permissions on the website backend. HTTPS is required in deployment. Do not paste credentials into chat.

- `GET /api/website-integration/products`, header `x-website-key: <server-side secret>`: returns active products and `nextOffset` (pages of 100). Fetch all pages. Each row has the product ID and `updated_at` version. Results are not a transactional snapshot: during concurrent edits pages may shift. Do not delete website records merely because they were missing from one run; reconcile safely.
- `PATCH /api/website-integration/products/:id`, same header: JSON requires `expectedUpdatedAt` exactly as returned plus one or more `name`, `category`, `model_specs`, `description`, or `price_raw` fields. A stale version or wrong-tenant ID returns 409; reload and resolve the conflict rather than overwriting. No other fields or image URLs are accepted. Text must be escaped by the website at rendering. The API invalidates the current process's AI cache; other processes may retain their short-lived cache until expiry.
- New products can currently be added only by an authorized catalogue manager using existing individual catalogue endpoints. A connected website can then read them. Image upload needs a private, tenant-scoped, validated storage pipeline and authorized serving; no safe upload is provided here. The AI should only use published/approved content.
- A developer must implement the custom website's server-side API client, update propagation/reconciliation, editor login/authorization, conflict handling, escaped rendering and monitoring. Preserve any existing site design. The API alone does not automatically update a website.

## Staging checklist

1. Inventory actual products, leads, profile and opt-out schema and current constraints/RLS/grants. Verify the live security and privacy issues in the earlier handoff; fix profile privilege escalation, storage, realtime and cross-tenant access before enabling this integration.
2. With backups and no production writes, apply `migrations/20261106_growth_features_STAGING.sql` only in a separate representative staging project. Verify the migration registry, service-role privileges, repeated application, rollback plan, and existing schema compatibility. The synthetic PGlite test is not a real Supabase integration test.
3. Use two test tenants, owners, assigned/revoked agency admins and a superadmin. Test direct REST/storage/realtime denial, key rotation, concurrent writes, stale versions and no private conversation access. Verify caching across workers and the real website client before rollout.
4. Complete image handling, safe creation and duplicates, authenticated WhatsApp submission/review, sync and failure recovery. Keep sensitive material private and confirm that client users remain view-only. Test with synthetic images and products.
5. Complete the review sender and learning workflow as described above, test consent, opt-outs and provider rules, then conduct an approved staging test. Do not send real messages or change live customer records without explicit authorization.
