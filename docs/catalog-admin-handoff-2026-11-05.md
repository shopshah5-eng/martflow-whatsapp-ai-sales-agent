# Catalogue administration: staging and Antigravity handoff

This branch contains a **partial, not production-ready** catalogue administration workflow. Do not deploy it to a live customer environment or apply its SQL until the prerequisites below have been reviewed, tested in staging, and approved by the owner. No live database, storage, deployment or WhatsApp message was changed as part of this work.

## What was implemented

- `/admin` and `/superadmin`, with catalogue sub-URLs and a link back to the dashboard. They reuse the existing browser session. Dashboard links use server-reported admin permission; Engineer Console links are hidden.
- A super admin can search existing account emails (prefix search, at least three characters; currently only letters, numbers, @, dot, plus and hyphen), enable/disable catalogue administrators, set a limit from 1–100, submit requests, approve/reject them, view and remove assignments, and open catalogues. Normal account creation remains separate.
- An enabled admin can request clients by registered email, see approved assignments, remove an assignment, and add, edit and delete products in approved catalogues. A request does not grant access until approval. No client organization membership is created.
- `migrations/20261105_catalog_admin_workflow_STAGING.sql` proposes service-role-only tables and RPCs. PostgreSQL row locks serialize quota and assignment changes per admin. Pending requests count toward the quota; removing an admin removes that admin's catalogue grants. Migration is **not applied** or tested against the actual database. It depends on the grants table and existing schema.
- The previous `/api/admin/catalog-permissions` write path is retired in the authoritative database (HTTP 410) to avoid bypassing atomic quota/approval rules. This is a compatibility change: existing clients using that path must be migrated in coordination with the UI and database. Existing grants are not automatically converted into admin accounts.
- Request-target query/body parameters no longer alter the inbox guard; own-workspace permissions and settings are checked without caller-supplied catalogue targets. Local synthetic API and DOM tests cover approval, quota, scoping, revocation, an inbox guard bypass and basic portal rendering. They are not a production security assessment.

## Required before rollout

1. Pull the active branch in the existing Antigravity project; preserve local modifications and the existing Supabase/Netlify/Render connections. Inspect the git diff and prior handoff `docs/audit-handoff-2026-11-05.md`. Never expose service-role credentials in browser code. Confirm the deployed revision rather than assuming a push deploys it.
2. Create a staging copy with backups, review actual schemas, profiles/memberships, grants, triggers, storage policies, functions and migration history. Review staged `20261105_staging_security_hardening.sql`, the earlier catalogue/security migrations and the new workflow migration; reconcile ordering, table columns/types, policies and rollback. Do not apply blindly to production. The live environment previously had public catalogue storage and broad tenant/profile permissions; API changes alone cannot guarantee conversation, settings or asset privacy. Check privileges including TRUNCATE, direct PostgREST, storage and realtime access as well as server routes. Prevent profile role/org manipulation and any cross-client membership that would allow inbox access. Test direct access as ordinary client, assigned admin, unassigned admin and super admin.
3. Decide how to migrate existing grants and limits. New admin accounts are not provisioned automatically. Reconcile existing legacy quotas (3–20 and local-only) with the new 1–100 database limits. Before rollout implement a careful backfill, compatibility/cutover plan and rollback; disabling or removing a new admin deletes their grants. The old write API intentionally returns 410 against Supabase. Do not leave a second grant path that bypasses locking, limits or approval. Review service-role access and all other grant mutation paths.
4. Run PostgreSQL integration tests against the staged schema with concurrent requests, approvals, removals, quota reductions, disabled accounts, failures/rollback, and attempts to call RPCs directly as anon/authenticated. Local in-memory tests are not concurrency or SQL tests. Verify actual profile email casing, owner identification and search behavior. Add pagination/chunking for admin/grant/request/profile queries and avoid incomplete results beyond PostgREST's row limit. Support literal underscore and other valid email-prefix characters safely. Improve actionable conflict/error messages without leaking account data.
5. Test the end-to-end portals with real signed-in staging accounts, session expiry/refresh, desktop/mobile, browser back/forward, direct URLs, empty/error/loading states and accessible keyboard interactions. Exercise assigned/unassigned catalogue reads and every mutation; verify ordinary users see no admin/engineer navigation. Verify client inbox, leads, WhatsApp pairing, settings, alert numbers, storage and realtime remain inaccessible to catalogue-only admins even with forged targets. A user may still access their own independently owned workspace as intended. Test against actual Supabase credentials without exposing them.
6. **Not implemented:** safe PDF, spreadsheet/CSV and website-URL imports. Build bounded, authenticated, tenant-scoped server-side parsing and a non-destructive review/confirmation workflow. Validate MIME, file size, parser behavior, content and storage isolation; never assume arbitrary PDFs/spreadsheets can be extracted reliably. Website fetches must validate and pin public destinations, handle redirects safely, and have strict size/time/rate limits. Present each parsed item and conflicts; auto-skip only fully exact duplicates and require human review for ambiguous matches. Make commit idempotent and atomic, ensure no silent updates/deletions or cross-tenant writes, and test malformed files, concurrent imports, duplicates and SSRF. The existing upload and website sync paths are not suitable substitutes: uploads are disabled in production and the old website sync can update same-name/SKU products without review. Disable or redesign unattended website sync until reviewed. Do not put confidential files in the existing public bucket.
7. Rerun the full suite and security tests, then perform staged deployment and explicit owner-approved production rollout only after backup, rollback and security/privacy verification. Keep unattended follow-up disabled until consent, opt-out, atomic claiming and provider-window requirements are verified. See `docs/whatsapp-call-alerts.md` for separate real-call staging verification; the call-alert code must neither answer nor reject calls.
