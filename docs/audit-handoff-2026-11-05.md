# Leadsy launch audit and Antigravity handoff — 5 November 2026

This is a risk-focused review, not a certification or proof that all defects were found. Audited baseline: `aaef417` on the Arena branch; changes accompanying this document are not automatically live. The existing homepage, hero and integration connections are intentionally untouched. Do not launch with real customer data until the critical items below are fixed and tested. Do not execute production changes from this document without an approved backup, staging validation, rollout and rollback plan.

## Confirmed live risks (read-only metadata, 5 November)

1. **Critical — public catalogue storage mutation and disclosure.** `catalogs` bucket is public; policies named `Allow Uploads Catalogs`, `Authenticated Upload Catalogs`, `Allow Updates Catalogs`, and `Allow Deletes Catalogs` apply to `public` and accept any object in that bucket. Public SELECT policies are also present. A more restrictive tenant policy does not override permissive policies. Verify with controlled synthetic objects in staging; investigate historical exposure and unauthorized mutations. Private bucket migration may break existing media URLs; plan signed/authenticated delivery and compatibility first. The staged `20261103_catalog_management.sql` is not proof of live enforcement.
2. **Critical — profile membership/role escalation and privacy.** `profiles_self_only` is an ALL policy; live `profiles` has no application privilege-protection trigger. An authenticated user appears able to update their own role/org fields directly through granted UPDATE, subject to actual column privileges and constraints; reproduce safely with test accounts in staging. The backend derives membership/privileges from profiles, so this may lead to role or tenant escalation. Existing `20261103_profile_privilege_guard.sql` is staging-only; reconcile with the live provisioning trigger and test signup and all legitimate changes first.
3. **Critical — direct Data API/realtime paths bypass app guards.** `conversations`, `messages`, `leads` and `products` have broad authenticated tenant-ALL policies. Conversation memories and follow-up schedules have tenant read policies. Those conditions do not distinguish client users from platform or agency catalogue managers. Live product policies allow tenant writes despite client view-only requirement. Review all related tables, storage objects, views, RPCs, logs, caches, realtime changes, backups and management consoles. SQL grants for anon/authenticated include broad privileges; RLS and grants must both be reviewed; do not assume RLS covers TRUNCATE. A privileged service-role or database operator can bypass RLS: absolute privacy from infrastructure operators requires a separate trust/encryption architecture, not UI or RLS alone.
4. **Follow-up is not ready.** Code has no validated, wired end-to-end production scheduler. Previously missing consent was treated as consent and ordinary inquiries marked consented; this patch removes those defaults. Durable opt-out writes and cancellation can be unawaited; reads may fail open, claims are process-local, pre-send verification and concurrent workers are not transactionally safe, and a valid approved-template/provider path has not been established. Keep follow-up disabled even if an environment flag exists. Build a durable per-workspace/customer consent ledger and opt-out, one unique schedule, atomic DB lease, cancellation, delivery-state handling and approved template send. Check cancellation immediately before send and handle ambiguous provider outcomes without blind retries. Test multiple workers, restarts, opt-outs, human takeover and database failure.
5. **Supabase migrations/deployment drift.** The live worker column, lead RPC, grant table, memory table and schedule table now exist, unlike the prior audit; migration history still reports empty, and several older broad policies persist. A script appears to have applied parts outside tracked migration history. Reconcile the real schema, RPC function bodies, grants and triggers against every migration before any deployment; never blindly replay SQL. Readiness checks do not prove permissions, WhatsApp, signup or revision alignment.

## Source fixes in this branch

- Restrict server conversation/lead/call/learning and WhatsApp session endpoints for platform and granted catalogue-only identities; fail closed if grant lookup fails. A catalogue grant now also removes inbox access for that identity. **This is intentional least privilege but can lock an existing client out if their account was also granted catalogue editing: create separate admin and client identities before rollout.** Database/storage/realtime policies are still live blockers.
- Website synchronization now validates all DNS answers, connects to a checked address, rejects redirects and credentials, applies response size/deadline bounds, and rejects special IPv4/IPv6 ranges. Catalogue sites that redirect will need their final direct URL. Shared remote attachment IP classification also rejects mapped/special IPs. Add network-level egress controls and staging integration tests; this is not a complete proof against every SSRF path.
- Dry-run chat uses the authenticated tenant instead of choosing the first local organization; test-audio is authenticated and access-controlled.
- Do not fall back to a second image matcher after stock/dedup checks; fix the two failing photo return assertions. Photo reservation is still in process memory and happens during generation, not confirmed delivery; dispatch, concurrency and restart behavior require further tests.
- Follow-up scheduling no longer infers consent and rejects delays under 72 hours. Normal conversation memory no longer asserts consent. This does not make follow-up production-ready.

## Antigravity execution plan

1. Fetch the latest Arena branch into the already-open project, without overwriting uncommitted changes. Confirm the exact commit and deployed Netlify/Render revisions. Preserve current connections and appearance. Review this handoff and `docs/launch-security-handoff.md` against current source; earlier reports may be stale.
2. Back up and inspect live schema, function bodies, triggers, RLS, grants, storage and auth settings. Prepare a **staging** migration to guard profile fields, replace broad storage policies, make catalogues private with compatible scoped delivery, enforce client-only conversations/lead data and admin-only catalogue mutation at every database/API/realtime path. Explicitly distinguish client identities from catalogue administrators and test privilege grants/revocation. Verify provisioning trigger continues to create one correct workspace and account, and audit privileged RPC EXECUTE grants and service-key use. Obtain explicit approval before production changes.
3. With two synthetic tenants plus separate platform admin, assigned agency admin, unassigned agency admin and client accounts, test allowed and denied reads/writes through API, direct Supabase anon/authenticated, Storage and Realtime; test revoked membership/grants and outages. The service role is never sent to browsers. Test signup, confirmation, email/password login, reset/change password, expired sessions and OAuth redirect on the actual domain. Inspect auth redirect settings and SMTP deliverability without exposing secrets. Do not assert an unauthenticated redirect to login is a failure.
4. Test WhatsApp pairing/reconnect, duplicate and concurrent inbound events, takeover, isolated memory, catalogue/stock edits, exact photo and brochure dispatch, failed sends and restarts using explicitly approved test numbers only. Audit B2B webhook authenticity, timestamp/replay/dedup and consent before any outbound messaging; remove unreachable legacy handlers only after route compatibility tests. No real customer messaging without explicit permission. WhatsApp Business Platform policy requires opt-in, approved templates outside the 24-hour service window, and a direct escalation path; using Baileys does not establish official-platform compliance.
5. Exercise retail/apparel (size/variants, stock), manufacturing (specifications, quantities, quotations), services/appointments (schedules, location, handoff), property (availability, appointments), healthcare (avoid diagnosis and minimize sensitive data), and multilingual/Hinglish users. Test uncertain answers, prompt injection, stale catalogue, inaccessible images, opt-out and human handoff. These are scenarios to validate, not claims of implemented industry features. Do not invent pricing, stock, policies or delivery promises. AI learning must be explicitly opted in, tenant-scoped, reviewed by humans, and have deletion/retention controls.
6. Review redaction, operational logs, backups, session storage, rate limiting, dependency advisories, abuse controls and incident response; record findings, tests, unresolved risks and rollback. The locally observed production dependency audit reported two moderate advisories, no high/critical; re-run with the actual deployment lockfile/environment. Obtain legal review of applicable India DPDP obligations and phased commencement, privacy notices, retention, erasure and processors; do not claim compliance from this document.
