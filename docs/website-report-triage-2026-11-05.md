# Website report triage — 5 November 2026

This document compares the supplied report with the source at the time of this change. The report's live observations are not independently re-verified here. A passing source test, an unauthenticated API denial or an RLS setting does not prove the deployed site, authenticated authorization, Storage or Realtime is secure. No live deployment, database/storage policy, auth setting or user data was changed. Review `comprehensive-audit-handoff-2026-11-05.md` for the wider blockers.

## Addressed in source

- Removed the old browser PDF.js and spreadsheet CDN scripts and the dormant browser parser code from both workspace and legacy admin pages. Import remains disabled; this is not an implementation of safe imports. Browser tests check both pages. Server dependencies and other parsing paths still need their own review.
- Rebuilt the legacy admin product table using DOM text nodes and event listeners rather than untrusted HTML/inline JavaScript, including error messages. The current `/admin` route already serves the newer catalogue portal. `/admin.html` now redirects to `/admin` in both Netlify rules and the Node server; any integration relying on the legacy direct page needs migration. No evidence of an actual exploit was established by this work.
- Removed query-string-based admin UI flags in the legacy page and its pre-filled personal email. Removed direct client-side profile/organization self-provisioning from its session handler; the backend session is checked instead. These changes do not remediate direct database policies.
- Removed inaccurate login-page encryption/privacy badges; no replacement statement should be interpreted as a security guarantee. Existing browser-stored provider keys are removed when the legacy engineer settings load, and the UI no longer stores or claims to save one. A previously exposed provider key should be assessed and rotated by its owner through the provider's secure console.
- Vendored and pinned one Supabase browser SDK distribution, with its license and integrity hash, for login, workspace and admin pages. The backend dependency is separate. Other externally loaded scripts and inline code still need review; this is **not** a strict CSP or comprehensive supply-chain remediation. Verify real email and Google login/session refresh on staging before rollout.
- Replaced the demo's delayed popup with a visible, user-clicked WhatsApp link after a successful enquiry. Added labelled inputs, inline status/errors and an explicit contact checkbox. The form itself does not send a WhatsApp message; the user must click and send. The number still depends on configuration/fallback and must be confirmed by the owner. The enquiry API now rejects overlong or non-string fields; the old shadowed server fallback that could dispatch a message has been removed.
- Unknown public paths now return an actual 404 in Netlify rules and the Node server, instead of homepage content. Added robots/sitemap, a 404 page, basic homepage metadata and favicon references, and `noindex` metadata for account pages. Existing explicit app/admin/API routes are retained. Verify routing and headers on a Netlify staging deploy, including OAuth callback/redirect and external links, before production.
- Removed the continuously running host-badge DOM polling/observer scripts, preserved the homepage design/hero image, added referrer and permissions headers, removed a deprecated response header, and added safe opener attributes to affected links. Long opaque WhatsApp IDs are no longer displayed as invented Indian phone numbers. Legacy suffix-based backend matching still needs a coordinated repair.
- Invalid keyed B2B webhook lookups now return a generic 401 without reflecting the key; malformed API JSON receives a JSON 400. This does not establish webhook authenticity, replay protection or safe outbound messaging.

## Unresolved / needs owner or staging action

1. **Storage and database privacy are release blockers.** The supplied report describes public catalogue listing and download; earlier read-only metadata also found broad storage and profile/tenant policies. Recheck effective current policies and object access with isolated test accounts. Prepare backups and a staging migration to private tenant-scoped delivery, role/profile guards, database grants and realtime restrictions; plan signed-URL and existing-link compatibility. Do not apply production changes without approval. Existing public links/files and earlier exposure require incident assessment.
2. **Signup and sessions:** verify actual provider email confirmation and Google identity linking with staging accounts, add anti-abuse controls and verify rate limiting. Do not silently alter live signup/auth settings. HttpOnly session architecture, reauthentication and the other login-security recommendations remain unimplemented. The anon key is designed to be public; correct policies are the security boundary.
3. **CSP and third-party risk:** inline event handlers, runtime CSS and remaining external resources prevent a safe strict CSP without refactoring and end-to-end testing. Migrate to reviewed, pinned dependencies and event listeners, then deploy a tested policy; do not add a restrictive header blindly and break the application.
4. **Legal and privacy:** obtain correct legal entity, contacts, processing purposes, retention, deletion, consent and grievance details from the operator and legal counsel; publish and link reviewed notices and terms. The contact checkbox alone is not a complete privacy notice. Do not invent a legal entity, officer or compliance certification.
5. **Demo and anti-abuse:** verify server validation and contact consent against the real flow. Per-identity throttles, CAPTCHA, durable anti-abuse budgets and comprehensive payload validation are not complete. The demo still needs a configured reachable number and an actual browser/provider test.
6. **Catalogue and admin:** safe PDF/spreadsheet/website import, ambiguous-match review, private storage, admin migration, direct REST/realtime restrictions and real concurrent quota tests remain unfinished. Review all remaining XSS/unsafe URLs and inline handlers; one table fix does not prove the application free of XSS.
7. **Messaging reliability:** investigate full-number identity matching, LID handling, message deduplication, webhooks, consent/opt-out, delivery failures, real calls and multiple-worker behavior. Existing tests are synthetic. The owner notification filter is heuristic and can miss or misclassify enquiries. WhatsApp calls must neither be answered nor rejected by the bot.
8. **Accessibility, performance, SEO and operations:** run real-browser accessibility and mobile tests, improve contrast, focus management and responsive layout, and measure real LCP/CLS. Home hero intentionally retained; optimize only without altering its appearance. Validate favicon/metadata/robots after deploy. Establish CI, dependency updates, monitoring, backups/restore and incident procedures. No legal or zero-vulnerability guarantee is made.

- Local HTTP tests cover a true 404, the retired legacy admin path, bounded enquiry fields, malformed JSON and non-reflective invalid webhook responses.
