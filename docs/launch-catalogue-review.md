# Catalogue and launch review

This is a prioritized review, not a certification that every issue has been found. Source and synthetic tests were reviewed; the current production database, authenticated browser sessions, and live messaging were not inspected or modified.

## Implemented in this branch

- Existing workspace members can view the catalogue. Workspace ownership alone no longer grants catalogue editing. Platform superadmins can explicitly grant/revoke an existing member's catalogue capability from `/admin`; every catalogue mutation checks current authenticated membership and the grant on the server. Grants default to denied and are scoped to a workspace. Revoking a grant takes effect on the next request; a request already in progress may finish.
- Managers can manually add, edit and delete products, pricing and specifications, and update the business knowledge used for catalogue setup. Client owners and members see no editing controls. The separate migration adds restrictive database policies, protects managed organization fields and disables direct catalogue-bucket writes. Legacy upload and AI-extraction routes also require the capability.
- The administrator must determine the genuine workspace ID and existing user ID, verify the agency person's identity and existing membership, and grant them deliberately. Do not grant customers merely because their role says `owner`. Recheck grants periodically and revoke access promptly. Changes to a profile's workspace revoke its old grants in the supplied migration.
- Authentication no longer manufactures a profile/workspace when the authoritative lookup fails. The local catalogue interface no longer reports direct database writes as successful when the server did not save them. An unscoped startup routine that rewrote matching customer organization/product records was removed.
- Manual catalogue management is the supported path in this branch. PDF/spreadsheet imports, website import, and catalogue image/brochure attachments are deliberately unavailable until secure durable storage and import handling are implemented and tested. Existing private-bucket attachments are not shown as public links. No existing product or file was deleted by this code change.
- This phase does **not** create agency-to-client assignments or a multi-workspace agency account. The Supabase membership model currently attaches a profile to one workspace. The superadmin page grants existing members access; it does not provide a cross-workspace product editor. The platform API has an explicit cross-workspace sync operation, but it replaces the provided catalogue and is not a substitute for a safe cross-workspace editor.

## Launch blockers and findings still requiring action

1. **Sensitive workspace information is exposed too broadly.** `/api/auth/me` returns the full organization record, `/api/settings` also returns it, and the organizations RLS policy allows tenant members to select organization rows directly. The schema includes webhook keys, WhatsApp credentials, pairing information and worker commands. Audit actual live grants and policies, separate secrets into server-only storage, return allowlisted public fields, and restrict sensitive reads and writes. The new catalogue migration does not fix this issue.
2. **Workspace members can perform sensitive actions outside the catalogue.** The schema's `wa_outbound_queue` policy grants tenant members broad operations, and the app also writes WhatsApp commands and queue items directly. A catalogue-view-only client is not automatically read-only across the rest of the product. Define role/capability checks for conversations, outbound messages, integrations, settings, and connections; move mutations behind audited, authorized APIs. Do not perform real-message tests without explicit consent.
3. **The live deployment appears out of sync.** Public probes of `/api/ready` on Netlify and Render returned `Cannot GET`; Render `/app` did likewise, even though current source defines these routes. Confirm the actual deployed revisions, environment variables, health/readiness paths, Netlify proxy routing and deployment logs. A healthy `/api/health` alone does not prove the full system works.
4. **Production schema and provisioning need reconciliation.** `supabase_schema.sql` and `migrations/001_initial_schema.sql` use different models; the organization security trigger references a field absent from the declared organization table, and the backend's fallback provisioning references additional columns not defined in the main schema. Audit actual columns, policies, triggers, grants and privileged functions before a migration. Test real signup, confirmation, Google callback, profile creation, removed membership and recovery against a disposable staging project. Missing profiles now fail closed rather than silently granting a new workspace.
5. **The migration is not applied to production.** The new server-side permission checks alone cannot stop direct Supabase access if older live policies remain. Stage `migrations/20261103_catalog_management.sql` with a backup, inspect all existing permissive policies and security-definer functions, and verify with real authenticated client, manager, platform and cross-tenant identities. Coordinate backend and schema rollout under maintenance or another safe cutover; do not expose a half-updated deployment. Confirm rollback and restore procedures before touching production.
6. **Private file workflows are incomplete.** Design per-workspace private object paths, validated content type and size, malware/content checks as appropriate, service-side authorization, short-lived signed reads and safe AI attachment retrieval. Test imports transactionally with previews, duplicate handling, explicit replacement and rollback. Avoid treating private bucket URLs as public or forwarding unvalidated URLs to external services. Preserve existing files until access and migration are verified.
7. **Other UI and operational issues remain.** The homepage and legacy admin page contain duplicated old dashboard code; remove or consolidate it after testing all routes. Some UI messages describe queueing as delivery, and other marketing/training claims require evidence. Review browser storage of session tokens, third-party scripts, CSP, error handling, logging of customer data, mobile accessibility and delivery-status UX. The current tests are not a substitute for a full security audit.
8. **AI and messaging need independent validation.** Confirm consent, opt-out, takeover, tenant isolation, delivery acknowledgements, approved product knowledge, hallucination handling, human escalation, and behavior in representative industries using synthetic data first. Learning from customer conversations needs explicit privacy/retention controls, review and approvals before using it for any training or sharing. Never assert guaranteed replies, security, or business outcomes.

## Verification and safe rollout checklist

- Local `npm test`: 113 tests passed, including explicit permissions, revoked membership and grant, forged role, cross-tenant attempts, database errors, and view-only/manager UI checks. Tests use local or mocked services.
- The migration and restrictive RLS behavior were simulated with PGlite, including a deliberately broad older permissive policy. This does not prove the migration matches the live Supabase schema or all existing policies.
- Take an encrypted backup and verify restore. Inventory actual schema and policy state. Apply the incremental migration in staging, run it again to verify idempotency, then run tests against real RLS as authenticated users. Ensure direct product/storage/managed-field writes are denied and service-side writes succeed only with the proper grant. Check reassigning a profile revokes its grant.
- Verify approved agency members already exist in the intended workspaces. Provision a trusted platform superadmin through an operator-controlled process; never expose the service key or platform secret in browser code. Use `/admin` to grant individual IDs, test revocation, and retain an operator audit trail; the present grant table records the grantor but is not a complete immutable audit log.
- Test catalogue CRUD and business knowledge with real test accounts in at least two workspaces, including denied client writes and cross-tenant IDs. Verify sign-up, login, recovery, refresh and revocation; visually check desktop/mobile. Then validate only consented test messaging and AI behavior. Do not claim readiness until all blockers are resolved and verified.
- No live migration, deployment, authenticated production test, real customer message, or WhatsApp session action was performed during this review. Keep PR #1 open; do not merge unless the owner explicitly approves.
