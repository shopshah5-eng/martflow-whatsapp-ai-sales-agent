# Launch security handoff — 2026-11-03

This is a prioritized review, not a security certification. Do not consider the site ready for launch until the live issues are fixed and independently verified. The project was inspected only using read-only Supabase metadata queries; no live database, bucket, customer record, WhatsApp session or message was changed in this review. The current changes are in branch `arena/a048d03f-martflow-whatsapp-ai-sales-age`.

## Critical live findings

Supabase project `martflow-ai-sales` (`uriqhusalcdgdlgzgasp`) was healthy at inspection, but health is not authorization. Migration history returned empty; inventory actual SQL state before assuming any migration has run. Policy/column metadata and triggers were inspected; no exploit was attempted.

- `profiles_self_only` is permissive ALL for a user's own row; `role` and `org_id` are writable and no profile triggers were found. The API's production membership lookup uses that profile, so a modified profile can change workspace and privileges. API checks alone cannot stop this. Investigate impact and other indirect paths. Stage `migrations/20261103_profile_privilege_guard.sql` only after checking all provisioning paths and security-definer functions. It blocks client profile inserts/deletes and membership-field updates, but does not by itself harden other tables, security-definer RPCs, or already modified rows.
- Organization members can select full organization rows directly; sensitive keys/tokens and pairing information may be exposed independently of the API. Broad update and authenticated insert policies and no organization triggers were observed. Audit and remove direct access to secrets and sensitive updates/creation; rotate affected credentials after closing exposure, with coordinated provider changes. Restrict pairing material to authorized roles. Move worker control, connection status/settings and provisioning to authorized server APIs; migrate all direct `select('*')` and writes in browser code before restricting access.
- `products_tenant_isolation` and `wa_outbound_queue_tenant_isolation` permit ALL to members. Catalogue grants and the two staged restrictive migrations were not reflected in observed live policies. Client-side UI restrictions do not secure direct database calls. Establish server-side role checks for all actions and real RLS tests.
- The `catalogs` bucket is public, and legacy public/permissive storage policies allow writes/deletes. Public URLs bypass object read policies. Audit existing objects and usage, migrate to private storage and short-lived authorized downloads, replace public URLs and restrict direct writes. Setting the bucket private before replacing links will break existing files. Review other buckets too, including session backup access.
- Live `organizations.catalog_pdf_name` was absent. The staged organization field triggers now compare optional columns through JSON rather than dereferencing missing columns, but other functions/queries may still expect missing columns. Reconcile the entire live schema and RPCs before deploying anything. The PGlite test represents only a small synthetic schema, not the real project.

## Local changes in this branch

- Login's direct-profile fallback no longer manufactures an owner role or catalogue permissions after backend verification fails; membership/capabilities must be verified by the server. Missing membership role is now treated as `member`, not a role claimed in a token. Local login no longer selects an unrelated organization if its membership is invalid, and login only returns the webhook key to privileged roles. The API allowlist now withholds pairing data from non-admin roles, but live direct database access still exposes it.
- The old backend production signup, which used admin-created email-confirmed users and issued a session without verifying email, is disabled. The browser uses Supabase signup, but working verified signup depends on actual Supabase confirmation settings and trusted profile/workspace provisioning; verify those before rollout. If the Supabase client is unavailable, the old backend fallback returns unavailable rather than bypassing verification.
- Anonymous enquiries/simulation require an explicitly configured isolated `DEMO_TENANT_ID` in production. Until configured, they return unavailable rather than writing to an assumed tenant. Configure and monitor the correct dedicated destination. Meta webhook verification no longer accepts a hardcoded fallback secret; set a unique `WHATSAPP_VERIFY_TOKEN` and `META_APP_SECRET` in the server environment.
- Conversation mode recognizes both legacy `manual` and `human`, and mode changes go through the authorized API. Manual-reply UI checks individual errors, retains failed drafts, avoids concurrent submissions and says queued rather than delivered. This direct-write workflow is **not** atomic and does **not** fix the live queue policy; a partially saved message or unknown queue status requires checking before retry. Replace it with an atomic authorized backend workflow.
- SQL migrations are staged, not applied. Restrictive profile guard and existing catalogue/queue guards were tested against intentionally permissive legacy policies in synthetic PGlite, twice for idempotence. Catalogue/organization trigger comparisons handle missing optional columns. Trusted service-side operations still require real staging validation.
- `npm audit --omit=dev` reported nine moderate transitive/direct advisories, including `exceljs`; assess safe remediation and reproducible dependency management. There is no committed npm lockfile under current conventions. Do not assume the audit covers a full supply-chain review.
