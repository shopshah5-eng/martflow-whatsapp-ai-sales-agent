## Changes in this audit (source only)

- Align Netlify clean admin/catalogue routes with the dedicated catalogue portal. Restrict catalogue operations, own-workspace reads, target-org checks and sensitive configuration access; correct missing repository import and broken AI extraction references. Remove a broken, unscoped learning synonym lookup rather than leaking data between organizations.
- Isolate incoming message deduplication, anonymous conversation/photo/link tracking and LID-to-phone mappings by workspace; remove hard-coded phone/LID associations and demo owner-number fallbacks. An unknown LID is withheld rather than guessed. This can suppress legitimate messages until validated mappings are available. Test against real devices before rollout.
- Phone ownership alone does not establish authenticated catalogue-admin rights: WhatsApp catalogue changes, stock/offer changes, document import and website commands are disabled. Read-only list, owner notes and workspace mode controls remain. Previous tests expecting catalogue mutation via WhatsApp were removed and replaced with denial tests. Legacy mutation code remains behind the guard and must not be re-enabled without an authenticated authorization design. Notes are tenant knowledge, not a trusted catalogue import.
- Owner note and undo persist locally and detect Supabase update errors. Workspace manual/automatic mode no longer changes the global legacy bot flag or resets every customer conversation, and local mode changes persist. Verify end-to-end production behavior before relying on them.
- Reject destructive bulk catalogue replacement and unattended website product sync; hide clear-all/upload controls and explain the limitation in the dashboard. Individual product changes remain subject to manager and target-workspace authorization. The old upload endpoint remains disabled in production. These safeguards are not the requested import feature.
- Fail closed when production provisioning finds no existing profile instead of running the non-atomic fallback. Existing valid trigger-provisioned profiles remain usable. If the signup trigger is missing or broken, affected users will see an error until a transactional provisioning solution is deployed. Verify trigger behavior in staging.
- Added regression tests for actual API access, extraction, tenant identity, WhatsApp controls, conversation tracking and disabled destructive flows. The staged catalogue-admin migration also has a synthetic PGlite test for basic quota/approval/privileges. This is not a substitute for real PostgreSQL, parallel-transaction, RLS, storage, realtime, browser, or provider tests.

## Critical blockers and remaining security weaknesses

1. **Direct database and asset privacy:** read-only inspection of the live project previously found a public `catalogs` bucket and broad public storage policies, broad tenant policies on conversation/message/product data, a self-ALL profile policy and broad grants. Verify current state rather than assuming these observations still apply. API-only restrictions cannot secure direct PostgREST, Storage, Realtime or service-role paths. Audit all effective policies (permissive policies combine with OR), column/table/function grants including TRUNCATE, views, triggers, RPCs and profile role/org mutation. Build and test replacement RLS, narrowly scoped grants and protected profile fields. Use private tenant-isolated assets and scoped delivery with a compatibility plan for existing links. Validate that clients cannot edit products and catalogue-only admins cannot access client inboxes, settings, owner numbers, pairing sessions, leads, files, realtime or backups. Service-role/infrastructure operators bypass RLS; absolute privacy from them needs a separate trust/encryption design.
2. **Phone matching and human takeover:** legacy paths in `server.js`, `takeoverService.js`, the adapter and manager still use last-ten-digit/suffix matches. Two international numbers can collide, misassociate messages or affect the wrong conversation, alert or takeover. Normalize to validated full international identities, backfill existing values with collision review, enforce tenant-scoped uniqueness and update all lookup/command paths together. Ambiguous legacy numbers must fail closed, not silently choose a match. Test both countries sharing a suffix, formatted/old records, owner commands, expiry, multiple workers and restart. Also verify database error handling and manual-mode state before sending; do not treat local mode tests as proof of delivery behavior.
3. **Migration/schema drift:** actual production migration registry was observed empty despite objects existing. Inspect live schema, all policies and RPC bodies before preparing a reversible staging plan. The staged admin migration depends on existing tables and has not been applied to live. Test genuine concurrent quota/request/approval/removal and privilege escalation attempts in PostgreSQL. Back up, plan rollback and obtain explicit approval before any production schema or storage changes.
4. **Follow-up/outbound consent:** keep unattended follow-up disabled. Consent/opt-out must be durable and fail closed; atomically claim schedules across workers, cancel on opt-out/takeover, recheck immediately before send, respect provider rules and avoid blind retries on ambiguous sends. Verify opt-in, approved templates/windows and human escalation for the chosen provider. Baileys usage does not itself establish official WhatsApp Business Platform compliance.
5. **Messaging identity and reliability:** unresolved LIDs currently produce no bot reply, and valid mappings depend on available provider metadata; test linked devices, LIDs and phone JIDs with explicit permission. Duplicate/fingerprint caches and photo-send reservations are process-local; multi-instance/restarts, concurrent events, queue ordering, delivery failures, reconnects and idempotence need a durable design. Avoid PII or content in logs, configure retention/redaction and restrict access. Review every handler and RPC for suppressed database errors, non-atomic updates and cross-tenant cache keys.
6. **Public ingress and outbound network security:** review webhook signature/authentication, replay and durable event deduplication, rate limits, origin/CORS, secrets, file parsing and all outbound requests. Website fetching now checks DNS, pins an accepted address and refuses redirects, but this does not prove all SSRF paths safe. Add network egress restrictions, redirect policy and adversarial tests. Review abuse/denial-of-service, session storage and secret rotation. No guarantee of zero vulnerabilities.
7. **Signup, provisioning and identity:** verify the real signup trigger creates exactly one correct workspace/profile for verified email/password and Google signup, handles retries/concurrency and rejects revoked or inactive users. Replace fallback with a reviewed transactional, idempotent service-only RPC. Verify profile field immutability, session revocation, confirmation/reset emails, Google OAuth consent, verified-email identity linking and allowed redirect URLs on the actual domain. Never ask clients to share OTPs or passwords. The previously requested secure operator invitation/delegation flow is not implemented.

## Missing features and functional work

- **Admin/superadmin:** staged portal supports signed-in account lookup, admin enable/disable and limits, requests, approvals, client removal and item-level catalogue management, but production SQL, legacy grant backfill/cutover and full UI/browser tests are outstanding. Add safe pagination/chunking and support valid email prefix characters such as underscore; handle PostgREST row limits, disabled accounts, conflicts, session refresh and browser navigation. Confirm superadmin bootstrap and actual account roles. Decide compatibility of the retired legacy grant write endpoint (410 in Supabase). Test role/grant revocation and approval races, and ensure separate client/admin identities when needed to preserve client inbox access.
- **Imports:** implement safe PDF, spreadsheet/CSV and website ingestion with bounded files, malware/format checks where appropriate, isolated private staging, SSRF defenses, structured preview, provenance and manual confirmation. Auto-skip only exact duplicates; ambiguous matches require review. Commit idempotently and atomically; never silently delete or replace existing products. Test malformed documents, empty extraction, duplicates, collisions, partial failures, retries and concurrent imports. Current disabled paths are not substitutes.
- **WhatsApp calls:** the helper is designed to notify the same workspace owner, not answer or reject the WhatsApp call. It has synthetic tests only; exercise real approved test calls, duplicates, offline/reconnect and multi-worker delivery in staging and validate provider behavior.
- **Pairing:** client signs up/logs in and pairs their own WhatsApp using Linked Devices via QR or pairing code. Verify real signup, QR expiry, pairing, reconnect, disconnection, tenant isolation and encrypted session storage. Admins must not see another client's pairing data.
- **AI quality:** research customer behaviour across industries and test realistic manufacturing, retail, services, property and multilingual/Hinglish conversations. Ground prices, stock and product details in approved current data, avoid invented claims and wrong images, escalate uncertainty to humans, handle malicious prompts and privacy-sensitive queries, and validate metrics with human review. Learning from conversations needs explicit opt-in, tenant isolation, review, retention/deletion and opt-out; no automatic cross-tenant training. The existing prompt/playbook is not evidence of quality or safe autonomous learning.
- **Existing homepage and journeys:** preserve supplied design, blended hero and current Supabase/Netlify/Render connections. The direct WhatsApp CTA uses public config and a fallback number; verify that the intended number is controlled, linked and actually reachable. Test all links, responsive layout, accessibility, loading/errors, session expiry, dashboard navigation and mobile devices. Previously requested live-test panel removal and enquiry-to-WhatsApp CTA are in source; confirm deployed revision.
- **Operations:** pin and reproducibly install dependencies with a reviewed lockfile and CI; `npm audit --omit=dev` locally reported two moderate findings in exceljs/uuid, no high or critical (not a complete vulnerability review). Reassess safe upgrades and parser risk. Add monitoring, health/dependency checks, error redaction, backup and restore drills, staged releases, rollback, incident handling and applicable legal/privacy review. Test actual deployed commit and configuration without exposing secrets.
